# agents.md

Guidance for AI coding agents (and humans) working in this repository.

## What this project is

`mailwizz-cli` is a Go command line client for the MailWizz REST API. Its command tree mirrors the
API resource structure (for example `mailwizz-cli lists subscribers create`). The API client and the
CLI command tree are generated from `openapi/schema.json`, MailWizz's OpenAPI 3 schema, so that
updating the schema and regenerating produces an up to date CLI without hand-editing dozens of
command files.

## Repository layout

- `cmd/mailwizz-cli/` - the CLI entry point (`main.go`), wires together hand-written and generated
  commands into the root application.
- `cmd/mailwizz-cli-gen/` - the code generator entry point, run via `task generate`.
- `internal/apiclient/` - hand-written low level HTTP client (auth header, query/multipart encoding).
- `internal/config/` - hand-written config file (`~/.mailwizz-cli.json`) and env var handling.
- `internal/output/` - hand-written response printing and exit code mapping.
- `internal/commands/` - hand-written commands not covered by the schema, currently `config`.
- `internal/generated/api/` and `internal/generated/cli/` - generated code. **Never hand-edit files
  in these directories.** Every generated file starts with
  `// Code generated by mailwizz-cli-gen. DO NOT EDIT.` If something here needs to change, change the
  generator (`generator/`) or `generator/overrides.yaml`, then run `task generate`.
- `generator/` - the schema parser, internal model (IR), overrides file, and templates used to
  produce `internal/generated/**`.
- `openapi/schema.json` - the source of truth. When MailWizz publishes a new version of this file,
  replace it and run `task generate`, then review the diff in `internal/generated/**` before
  committing.
- `.github/workflows/ci.yml` - build/lint/test/generate-check on every push and PR.
- `.github/workflows/release.yml` and `.goreleaser.yaml` - cross-platform release binaries, published
  on `v*` tags.

## Workflow

- `task generate` - regenerate `internal/generated/**` from `openapi/schema.json`.
- `task generate:check` - regenerate and fail if the working tree then has uncommitted changes under
  `internal/generated/**` (used by CI to catch a stale schema/codegen mismatch).
- `task lint` - run golangci-lint (`.golangci.yml` enables effectively every linter).
- `task test` - run the test suite with the race detector.
- `task build` - build the `mailwizz-cli` binary into `bin/`.
- `task check` - everything CI runs: generate:check, lint, test, build.
- `task release:check` - validate `.goreleaser.yaml`.
- `task release:snapshot` - build every release platform/arch locally into `dist/` without publishing.

Run `task lint` and `task test` before considering any change finished.

## Releasing

`.goreleaser.yaml` builds `mailwizz-cli` for macOS, Linux, and Windows on amd64 and arm64.
`.github/workflows/release.yml` runs GoReleaser and publishes a GitHub Release whenever a `v*` tag is
pushed. Do not hand-edit build artifacts; change `.goreleaser.yaml` and validate with `task
release:check` / `task release:snapshot`.

## Conventions

- Keep hand-written code simple, idiomatic Go that a human can read without needing generator
  context: short functions, descriptive names, standard error wrapping with `fmt.Errorf("...: %w",
  err)`.
- When a golangci-lint rule genuinely conflicts with writing clear, idiomatic Go for a specific line,
  prefer a narrow `//nolint:<linter> // reason` on that line over disabling the linter project-wide.
  Only disable a linter entirely in `.golangci.yml` when it is deprecated or fundamentally does not
  fit this codebase, and say why in a comment next to the disable entry.
- Comments and documentation should read like they were written by the person maintaining the code:
  no emojis, no em dashes, and nothing that signals the text was produced by an AI tool. Write plain,
  direct sentences.
- Only comment code where the "why", not the "what", needs explaining. Do not narrate obvious code.
- New hand-written commands go in `internal/commands/`; new API-backed commands come from the
  generator, not by hand.
- Tests live next to the code they cover, using the `_test` package suffix (black-box tests) unless a
  test needs access to unexported internals.

## Adding or changing an API operation

1. Update `openapi/schema.json` (or wait for an upstream MailWizz schema update).
2. If the new/changed operation does not fit the generator's default naming rules (see
   `generator/model.go`), or needs a flag the schema does not declare (for example pagination), add or
   update an entry in `generator/overrides.yaml`.
3. Run `task generate` and review the diff.
4. Run `task check` before committing.
